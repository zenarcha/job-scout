What happened

Two sessions so far: one built the working system, one reframed where it’s headed.

Session 1 — Built the tracker, went live

2026-07-10 · Phases 0–3

Planned across five refinement rounds, from a basic job scraper into a fuller system, then built end to end:

  • Discovery — ingest from Apify + ATS feeds, cross-source dedup, source-reliability ranking
  • Enrichment — five versioned AI stages: classify, resume-match, skills, salary (parsed only, never guessed), recommend
  • Notifications — Telegram (instant for high-priority, digest otherwise) + Notion sync
  • Went live — created Supabase project job-tracker (ap-south-1, $0/mo), applied schema, seeded an 11-company watchlist

Everything runs on free tiers, with Gemini as the default AI provider, swappable to Cerebras or Grok.

Session 2 — Reframed as an Application OS, prepped the schema

2026-07-10 · Product evolution + lane-ready prep

A synthesis brought in the idea that this tracker is the foundation of something bigger: an AI Job Application OS — discover, qualify, prioritize, and execute applications with minimal manual effort. Guiding rule: evolve, don’t rewrite; extract capabilities, don’t merge projects.

  • Qualification over recommendation — AI will emit structured signals, not a final verdict
  • A deterministic Lane Engine reads those signals and computes a lane — see below
  • Lane ≠ Urgency — strategy and timing were split into two independent concerns
  • “Interest” retired — replaced by Personal Preference (yours), Opportunity Score (AI’s), and one active Goal
  • Discovery generalized to accept a future Chrome extension and manual imports, both AI-free
  • Application Assets (resume, referral, outreach, cover letter) stays on the roadmap — schema deliberately deferred until the existing prototype projects are studied
  • Architecture then frozen — further ideas go to a backlog, not into a redesign

To prepare without changing behavior, an additive migration added empty signal/lane/urgency columns and an inbox status — nothing reads them yet.

Lanes, explained

The concept you asked about. Proposed in Session 2, not yet built — the columns exist, but nothing computes a lane today.

Lane AReferralHigh background match → referral outreach + a tailored resume.
Lane BBuilderBuilder-culture, remote startup, portfolio valued → a product artifact + founder outreach.
Lane CPracticeWorth applying, not a priority → resume only.
Lane DSkipNot worth pursuing right now.
Why the AI doesn’t just say “Lane A”: the AI only outputs neutral measurements — background match, builder culture, referral value, portfolio value, and more. A separate, plain Lane Engine applies configurable rules to those measurements to pick the lane. When your strategy changes, only the rules change — every stored job can be re-sorted without re-running any AI. Lane answers “which application strategy”; a separate urgency field (deadline, job age, freshness) answers “how fast to act” and drives alert timing instead.

Architecture, at a glance

Nine standing principles carried the design through both sessions. The shape hasn’t changed since — only the schema grew additively.

Data model

  • jobs — immutable, exactly as scraped
  • job_enrichments — versioned AI output, one active row per stage
  • job_tracking — your edits: status, notes, locked fields
  • job_events — append-only bus and audit trail

Pipeline stages

  • classify → resume-match → skills → salary → recommend
  • each stage independently retryable, never blocks the others
  • reserved for later: a qualify stage, no rename yet

Trust & safety rails

  • confidence < 0.6 → flagged for review, never auto-applied
  • manual overrides lock a field against future AI writes
  • salary is parsed only — never a guess
